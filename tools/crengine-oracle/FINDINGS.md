# crengine-xpointer — oracle integrity findings (2026-10-06)

## The bug found

`tools/crengine-oracle/src/oracle.cpp` built documents with `new ldomDocument()`
and never registered crengine's element/attribute/namespace tables. Consequence,
measured by instrumenting crengine itself: every tagname was allocated an
"unknown element" id (`body` -> 512 instead of `el_body` = 22, `DocFragment` ->
513 vs 9, `div` -> 515).

Therefore, in every committed oracle run:

- no `id == el_body` / `el_DocFragment` / `el_head` match fired anywhere;
- `ldomNode::applyNodeStylesheet()` was never called -> a book's own CSS
  (`<style>`, `<link rel=stylesheet>`) was collected into
  `<DocFragment><stylesheet>` and then ignored;
- `_typeDef` was null, so the tag table's `display` / `white-space` never
  applied, and `ldomElementWriter`'s `_isBlock` kept its constructor default
  (`true`), which is what was really driving the whitespace drops — not the tag
  table, as previously believed.

Fix (mirrors `lvdocview.cpp:4986-4988`):

```cpp
fixture->document->setNodeTypes(fb2_elem_table);
fixture->document->setAttributeTypes(fb2_attr_table);
fixture->document->setNameSpaceTypes(fb2_ns_table);
```

The tables are `static` arrays generated by `fb2def.h`'s X-macros, so the oracle
must instantiate them itself:

```cpp
#define XS_IMPLEMENT_SCHEME
#include "fb2def.h"
#undef XS_IMPLEMENT_SCHEME
```

Also added while debugging, and kept because they are provenance the committed
data should carry: `ORACLE_FONT` (font manager + `setRenderProps`, else no CSS
applies at all), `ORACLE_UA_CSS`, `ORACLE_WIDTH`/`ORACLE_HEIGHT`,
`setContainer(LVOpenDirectory(dir))` + `appender.setCodeBase(file)` (without a
container `applyNodeStylesheet()` returns early), `docFlags` in the output, and
per-element computed `display` / `whiteSpace` / `block` / `pre`.

## Verified facts about the device pipeline (KOReader reading an EPUB)

- KOReader passes UA CSS as **text**: `readertypeset.lua:40` ->
  `credocument.lua:1333` -> `koreader-base/cre.cpp:1760`, which reads the file
  with `LVLoadStylesheetFile` — that helper resolves one level of `@import`
  itself and prepends it (`lvstsheet.cpp:8423`, `css = txt2 + s`) — then
  `LVDocView::setStyleSheet(css, false)` ->
  `ldomDocument::setStyleSheet(text, replace=true)` ->
  `_ua_stylesheet.parse(text, true)`. So the device really gets
  `html5.css + epub.css` + style tweaks, in that order.
- Styles are on: `LVDocView::setRenderProps` runs during load
  (`lvdocview.cpp:4435`).
- `onBodyEnter()` ends with `_isBlock = isBlockNode(_element)`
  (`lvtinydom.cpp:6254`) and clears `TXTFLG_PRE` otherwise (`:6256-6261`), so
  with styles on the tag table's `display`/`white-space` are discarded and only
  computed CSS counts.
- Text-node drop rule for EPUB (DocFragment path) is `lvtinydom.cpp:9024`: drop
  a whitespace-only text node iff it would be the element's **first** child AND
  the element is block-ish AND not pre-ish. `:9583` is the whole-document writer
  (html mode) instead.
- Block test is `display > css_d_inline && display != css_d_none`. Enum values:
  `css_d_inline=3`, `css_d_block=4`, `css_d_inline_block=7`, `css_d_none=18`.
- `html5.css` live `display`/`white-space` declarations: 22, of which only
  `pagebreak` and `fieldset` are `display: block`. The spec's flow-element block
  list is present but inside a `/* crengine-:` comment (`html5.css:130-135`), on
  the assumption the fb2def.h tag table covers it — which styles-on discards.
- `epub.css` live `display` declarations: **zero** at DOM version >= 20180528,
  because all of them sit inside `@media (-cr-max-cre-dom-version: 20180527)`.
- In the UA sheet, class selectors never match (`_ua_stylesheet.parse()` gets no
  `lxmlDocBase *`; class interning needs `_doc`, `lvstsheet.h:273`). Element,
  `[attr]`, `[attr=value]`, `>` and `:first-child` selectors do match. In
  **author** CSS, class selectors match normally (verified after the DTD fix).
- Net effect for a typical EPUB: almost nothing is block, so whitespace-only
  text nodes survive; the drop rule fires mainly on book CSS that declares
  `display: block|inline-block|table*|list-item`.

## Consequences

1. All committed oracle data (`src/__test__/oracle/crengine.json`) is invalid:
   produced against an uninitialized DOM, without styles, without a UA sheet,
   and with author CSS silently ignored. Regenerate.
2. The library's whitespace rule must default to **keep** the node, dropping
   only when computed CSS says block-ish — the current model drops far too much.
3. Oracle regeneration should use the production-equivalent UA sheet
   (concatenate `html5.css` + `epub.css` minus its `@import`, matching
   `LVLoadStylesheetFile`) plus new fixtures with author CSS: block,
   inline-block, none, `white-space: pre`, `@media` at two widths, linked `.css`
   via the container.

## The LVDocView path works, and the crashes were my harness

A standalone driver using `new LVDocView(-1, true)` + `Resize` + `LoadDocument`
on a real two-file EPUB (source: /tmp/viewprobe.cpp) loads cleanly and reports:

```
stylesEnabled=1 docFlags=b screenWidth=600
elements=11 text=6 whitespace-only=0 boxing=2
```

- A book's linked `style.css` applies through this path
  (`span { display: block }` -> d4) with **no crash**. The segfaults listed
  below only happen with hand-wired `ldomDocument` + writers, so they are
  harness artifacts of missing engine setup, not crengine bugs.
- `autoBoxing` nodes really are in the DOM (2 in a one-paragraph document,
  wrapping inline content), but `toStringV2()` never emits them: `<img>` inside
  a `p` that has autoBoxing children is addressed as `.../p[1]/img[1]`. So
  boxing nodes are invisible to xpointers and the library's "boxing is not
  addressible" model is correct.
- `text()[n]` indexes line up with the text-node siblings an xmldom parse
  produces.

Conclusion: drive the oracle through `LVDocView` instead of wiring writers by
hand. That path has done the three things the hand-wired one silently got wrong
(element tables, styles, container).

## Oracle ported to LVDocView

`src/oracle.cpp` now drives `LVDocView` instead of wiring `ldomDocument` +
writers: register the font from `ORACLE_FONT`, `new LVDocView(-1, true)`,
optional `setStyleSheet(uaCss, false)` (the reader's sheet, as a user-agent
sheet), `Resize(gWidth, gHeight)`, `LoadDocument(path)`. CLI is
`crengine-oracle <book.epub>`; `--mode epub|html`, the second legacy-DOM pass
and the `mode`/`legacyDomVersion`/`sameTree`/`legacyPointers` JSON fields are
gone, and `uaCssBytes` was added so a run that lost its sheet is visible in the
data.

Verified on a probe EPUB: 16 nodes (2 of them `autoBoxing`), 44 pointers, 95
resolutions, `stylesEnabled=true docFlags=11`, and the book's linked `style.css`
applied.

### Crash found: boxing nodes at offset -1

`ldomXPointer(boxingNode, -1).toStringV2()` **segfaults**; the same node at
offset 0 is fine. Normalized pointers never contain boxing nodes, so
`collectPointers()` skips them via `isPointerTarget()`; they are still dumped
(with `boxing: true`) so the library can see that crengine's tree has them.

### Still open

Does an `autoBoxing` child consume a sibling position for `[n]` indexes? It did
not affect `text()[n]` or `img[1]` in the cases measured, but it is unverified
in general, and it is the one thing that could make a device pointer
unresolvable against an xmldom tree (which has no boxing nodes).

### Remaining work for the port

1. Fixtures as real EPUBs: each fixture becomes a directory of chapters +
   optional CSS, and `generate.sh` zips them (`zip -0 -X mimetype` first, then
   `META-INF/` + `OEBPS/`), since `LVDocView` wants an archive.
2. `generate.sh`: build the UA sheet the way `LVLoadStylesheetFile` does
   (`html5.css` + `epub.css` minus its `@import`, from the pinned crengine

   `crengine.version`.
3. `src/__test__/oracle.test.ts`: drop the `mode`/legacy fields, rebuild the
   tree from the new shape, and regenerate `crengine.json`.

## Where whitespace actually goes (measured, 2026-10-07)

Two separate transformations, both of which a cross-parser implementation has to
predict.

### 1. At parse time, text is rewritten (not just dropped)

`LVXMLParser::ReadText()` runs every text token through `PreProcessXmlString()`
(`lvxml.cpp:5904`), which — unless the token is `TXTFLG_PRE` — converts `\r`,
`\n` and `\t` to a space and collapses runs of spaces to one. So the _stored_
text differs from the source, and `TrimDoubleSpaces()` (the trimming pass) is
not used for EPUB chapters: `TXTFLG_TRIM` is only ever set on the plain-text
loading paths. Measured: `<p>para <em>em</em> tail</p>` stores `"para "` and
`" tail"`; `<p>a\nb</p>` stores `"a b"`.

`TXTFLG_PRE` comes from the element writer (`lvtinydom.cpp:6026`, updated at
`:6256`), i.e. from the computed `white-space`, and additionally from `fb2def.h`
for `pre`-like tags and for text inside `<svg>`. `<pre>`/`<textarea>` also drop
a newline immediately after the open tag (`:6048`), and tabs inside pre are
expanded to 8-column stops (`lvxml.cpp:5913`).

Consequence: **a character offset in a device xpointer counts characters of
crengine's rewritten text**, so resolving one against an untouched parse needs a
position-preserving version of the same rewrite.

### 2. At render time, edge whitespace text nodes are deleted

`ldomElementWriter::onText()` only drops the first whitespace child of a block
(`:9024`), but `LVDocView` renders, and rendering runs
`ldomNode::autoboxChildren()` (`:6806`), which — when the parent is not
`white-space: pre` — walks the child run, steps over leading whitespace-only
text, steps back over trailing whitespace-only text, wraps what is left in an
`autoBoxing` node and **deletes** the nodes it stepped over
(`removeChildren(startIndex, firstNonEmpty-1)` / `(lastNonEmpty+1, endIndex)`,
`:6926-6932`). Runs with no inline content at all have their empty children
removed too (`:6949`).

Measured with `fixtures/spacing.xhtml`:

| source                         | children crengine kept              |
| ------------------------------ | ----------------------------------- |
| `<p>\n<b>x</b>\n y\n</p>`      | `<b>`, text `" y "`                 |
| `<div>\n<p>b1</p>\n<p>b2</p>`  | `<p>`, `<p>` (no text at all)       |
| `<p>m1<span>m2</span>\n</p>`   | text `"m1"`, `<span>`, text `" "`   |
| `<span>\n<i>s1</i>\n<i>s2</i>` | whitespace survives (inline parent) |

So "first child of a block" is _not_ the rule; the rule is CSS's —
whitespace-only text at the edge of an inline run (which includes every parent
edge, and both sides of a block child) is removed unless `white-space: pre`.
This is why the earlier "invert the library's default" idea and the earlier
"first child only" reading were both wrong.

The deletion happens in the DOM, not only in the box tree: the deleted nodes are
gone from the dump, and `toStringV2()` never names `autoBoxing`, so the rendered
tree the device addresses is `parse tree - edge whitespace - boxing nodes`, in
that order.

## What the cascade has to produce

Only two properties change the tree, so only two are modelled.

Enums (`crengine/include/cssdef.h`), as they appear in `crengine.json`:

- `display`: `inline=3`, `block=4`, `list-item=6`, `inline-block=7`,
  `inline-table=8`, `table=9`, `table-row=13`, `table-cell=16`, `none=18` — and
  crengine's own block test is
  `display > css_d_inline && display != css_d_none`, so everything from `block`
  to `table-caption` counts as block and `ruby`/`run-in`/`inline`/`none` do not.
- `white-space`: `inherit=0`, `normal=1`, `nowrap=2`, `pre-line=3`, `pre=4`,
  `pre-wrap=5`, `break-spaces=6`. Parsing is "pre" at `>= pre-line`; the
  parse-time flag is seeded from the tag table when the element opens and
  re-read from the computed style once the style is known (`lvtinydom.cpp:6026`,
  `:6256`).

Tag defaults measured from the new data (styles on, UA sheet on), i.e. what the
hand-authored default table has to reproduce:

| block                                                           | inline                                                                | table         | special                                                                                                                                     |
| --------------------------------------------------------------- | --------------------------------------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| body, div, h1, hr, p, pre, section, ul, DocFragment, autoBoxing | a, b, br, em, i, img, span, strong, svg, circle, stop, linearGradient | table, tr, td | `style` is `none` + pre; `li` measures **inline**, not `list-item`; `pre` measures `block`+**normal** while its children still parse as pre |

The two surprises are worth carrying into the library's "crengine deviations"
comment: `li` is not a block, and `<pre>`'s own computed `white-space` is
`normal` (the pre behaviour comes from the parser flag, so a stylesheet
`white-space` on `<pre>` cannot be trusted to restore it).

## Cascade implementation checklist (implemented 2026-10-07; the parity run corrected six of these)

1. `css.ts` — tolerant scanner producing `{ selectors, declarations, media }`.
   Skip `@font-face`/`@page`/`@supports` blocks; `@import` is ignored (crengine
   resolves those itself when it loads the file, and the EPUB loader already
   inlines one level).
2. `@media` — crengine evaluates `width`/`min-width`/`max-width` against the
   **page** width (`getPageWidth()`), height likewise, and `device-width`
   against screen width (`lvstsheet.cpp:2320-2360`). The oracle only ever passes
   one width to both, so one `screenWidth` input is enough; document that
   `max-width` means page width.
3. `selector.ts` — supported subset, from `css_pseudo_classes[]`
   (`lvstsheet.cpp:315`):
   `:root :dir() :first-child :first-of-type :nth-child() :nth-of-type() :last-child :last-of-type() :nth-last-child() :nth-last-of-type() :only-child :only-of-type :empty :is() :where() :not()`,
   plus `::before/::after/::first-letter/::first-line` (generated content is out
   of scope). Anything unrecognised must make the rule never match, which is
   what crengine does with a selector it cannot parse.
4. `cascade.ts` — precedence: UA normal < author normal < author `!important` <
   UA `!important` (`_ua_stylesheet` is consulted after author sheets, and
   tweaks are handed in through the same UA slot). Class selectors never match
   through the UA sheet, because `lxmlDocBase::setStyleSheet()` parses it
   without a document and class interning needs one.
5. `text.ts` — position-preserving version of `PreProcessXmlString`'s non-pre
   mode, plus the `<pre>`/`<textarea>` leading-newline strip and tab expansion,
   so a crengine text offset can be translated to the raw text an XML parser
   kept.
6. `view.ts` — `children(node)` = addressible children minus the edge
   whitespace-only text nodes `autoboxChildren()` would delete, and minus boxing
   nodes; `text(node)` and the offset maps from (5).
7. Parity test: parse `OracleDocument.source` with `@xmldom/xmldom` (skip
   fixtures whose source does not parse — `unclosed.xhtml`, and `tables.xhtml`
   where crengine foster-parents), then for every `pointers[]` entry check that
   resolving the string in the parsed tree lands on the node whose pre-order
   rank in the pruned tree equals the crengine id's rank, with offsets
   translated through (5).

## What the parity run corrected (2026-10-07)

`libraries/crengine-xpointer/src/__test__/parity.test.ts` parses each
fixture'"'"'s own chapter bytes with @xmldom/xmldom, builds a view from the
fixture'"'"'s stylesheet and page width, resolves every pointer the oracle
dumped, and builds each one back. All 17 parseable fixtures match in both
directions. Six claims above did not survive it:

1. **`<pre>` does compute `white-space: pre`, and an author rule can take it
   away.** `<pre class="norm">` with `.norm { white-space: normal }` dumps
   `pre=false ws=1` and its text arrives collapsed. crengine re-reads the
   computed style when it closes the element and sets or clears `TXTFLG_PRE`
   accordingly (`lvtinydom.cpp:6256`), so the element table only seeds the
   value. The dump for `pre.xhtml` is unambiguous: plain `<pre>` is
   `pre=true ws=4`, the one with the class is not.
2. **Tag defaults beat inheritance for `white-space`.** crengine'"'"'s element
   table holds a concrete value, not `inherit`, so `<pre>` inside a normal
   `<div>` is pre and a `<span>` inside that `<pre>` inherits it. CSS
   inheritance in the textbook order gets this wrong.
3. **Trailing whitespace of an inline run goes when a block follows.**
   `<p>a</p>\n<span>s</span>\n<p>b</p>` as body children keeps the whitespace
   after the span when it is the last thing in the parent (`spacing.xhtml`), and
   drops it when a `<p>` follows (`styles.xhtml`, where a `div` is
   `display: inline` and the run ends at a block). The rule is: delete a
   run'"'"'s leading whitespace-only text always, its trailing whitespace-only
   text only when the run is followed by a block child.
4. **Boxing nodes must be flattened, not skipped.** An empty inline at block
   level is wrapped in an `autoBoxing` node whose content is nothing, so
   `<span></span><br>` disappears entirely from the children an xpointer counts
   (`empty.xhtml`: seven children in the parse, five in crengine). Filtering the
   boxing nodes out leaves the wrapped content where the wrapper was, which is
   the same shape; keeping them, or filtering without promoting, loses or
   misplaces it.
5. **`<pre>` and `<textarea>` lose one leading newline.**
   `<pre>\n  keep\n  me\n</pre>` stores `"  keep\n  me\n"` (`spacing.xhtml`):
   one character, only as the element'"'"'s first child (`lvtinydom.cpp:9029`,
   flag set at `:6049`).
6. **A `<style>` in the body of a chapter is ignored.** `internal.xhtml` has
   `em { display: block } strong { white-space: pre }` in a `<style>` before the
   paragraphs that would match. The dump shows `<em> display=3` (inline) and
   `<strong>` with collapsed text: the sheet was attached — the element is in
   the tree, `display=18` — and had no effect on the chapter it sits in.

## Parser divergences the library cannot fix

- **HTML named entities.** `&nbsp;` is not XML. crengine decodes it;
  @xmldom/xmldom leaves the eight characters of source as text. Text and carets
  differ for any text that uses one, so the parity run counts those carets
  separately and a test pins the count above zero.
- **Repaired markup.** `unclosed.xhtml` is a fatal error for an XML parser and
  `tables.xhtml` loses content to foster parenting in crengine. Both are
  skipped, with the reason in the test. EOF head -3 FINDINGS.md; wc -l
  FINDINGS.md

## Not a divergence: HTML named entities (corrected 2026-10-07)

I had written `&nbsp;` up as a divergence — xmldom keeping the characters where
crengine stores one character — because the parity harness parsed the fixtures
as `application/xml`. That is the wrong media type. Parsed as
`application/xhtml+xml`, which is what `@storyteller-platform/epub` passes for
chapter content, xmldom decodes HTML named entities (its
`src/__test__/xml.test.ts` pins both halves: entities decode as XHTML; as
`text/xml` the entity is reported and survives as literal text). With the media
type corrected, the `unicode` fixture matches crengine text for text, entities
and astral characters included, and every caret in it resolves.

Keep it as a failure mode rather than a limitation: the wrong media type does
not throw, it keeps `&nbsp;` as six characters, so every caret after it counts
the markup and is off by five. `&unknownent;` still errors under XHTML, which is
the only signal that entity handling is happening at all.
